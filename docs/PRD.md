# 八字合盘匹配系统 — 产品需求文档（PRD）

> 版本：v1.0 | 日期：2026-06-05 | 作者：许清楚（产品经理）

---

## 一、项目信息

- **语言**：中文
- **编程语言**：后端 FastAPI + sxtwl + SQLite | 前端 Vue3 CDN + Tailwind CSS CDN + axios CDN（单 HTML 文件）
- **项目名称**：bazi-match
- **原始需求**：用户输入出生日期时间，系统从 1W 名虚拟用户库中匹配出八字合盘得分最高的用户，并展示详细合盘分析。核心卖点：娱乐向、结果可视化、分享友好。

---

## 二、产品定义

### 产品目标

1. **娱乐社交引擎**：以八字合盘为切入点，提供有趣、易懂的匹配体验，让用户在 3 秒内获得可视化合盘结果，激发分享传播
2. **专业感与信任度**：六维度加权评分体系（地支合冲/五行互补/天干合/日主关系/纳音/神煞）让结果有理有据，模板化解读增强"被算到了"的体验
3. **零门槛单机部署**：单 HTML 前端 + SQLite 数据库 + FastAPI 后端，无需云服务，一键启动即可使用

### 用户故事

1. **As a** 好奇用户，**I want to** 输入自己的出生日期时辰和性别，**so that** 我能快速看到与谁八字最合，满足好奇心
2. **As a** 社交用户，**I want to** 查看匹配结果的各维度得分和解读文案，**so that** 我能把有趣的结果截图分享给朋友
3. **As a** 八字爱好者，**I want to** 查看合盘详情弹窗中每个维度的进度条和具体命中（如"子丑合"、"寅申冲"），**so that** 我能理解评分依据而不仅是看总分
4. **As a** 移动端用户，**I want to** 在手机浏览器上流畅使用，**so that** 我随时随地都能玩
5. **As a** 运营人员，**I want to** 一键部署系统（无需数据库服务器、无需构建工具），**so that** 我能快速上线验证产品效果

## 三、技术规范

## 四、UI 设计稿描述

### 整体风格

- 单页应用，无路由，三个状态切换（input → loading → result）
- 主色调 **indigo-600**（#4F46E5），背景色 gray-50/slate-50
- 卡片白色，圆角阴影（rounded-lg, shadow-md, border border-gray-200）
- 容器 max-w-2xl mx-auto p-6，居中布局
- 响应式：移动端单栏全宽，桌面端可双栏（P2）

### 状态1：输入表单（默认）

```
┌──────────────────────────────────────┐
│  🏮 八字合盘匹配                    │
│                                      │
│  出生日期：  [2000-03-15]            │
│  出生时辰：  [未时 13:00-15:00 ▼]    │
│  性别：      (●) 男  ( ) 女         │
│  匹配数量：  [5]                     │
│                                      │
│  [  开始匹配  ]  (bg-indigo-600)     │
│                                      │
│  ⚠️ 仅供娱乐参考                    │
└──────────────────────────────────────┘
```

- 出生日期：`<input type="date">`，范围 1940-2010
- 出生时辰：`<select>` 下拉，12 个选项（子时23:00-01:00 ... 亥时21:00-23:00），选中后取中间值传后端
- 性别：`<input type="radio">` 男/女
- 匹配数量：`<input type="number">` min=1 max=20 默认=5
- 验证不通过：按钮 disabled + 红色边框提示
- 免责声明：页面底部，醒目位置

### 状态2：加载动画（1-3秒）

```
┌──────────────────────────────────────┐
│                                      │
│        ⏳ 正在匹配中...              │
│                                      │
│        [==========>_____] 进度条     │
│                                      │
│        已匹配：5823 / 10000          │
│                                      │
└──────────────────────────────────────┘
```

- 假进度条：setInterval 每30ms progress+1，从0到90%
- 同时发起 axios POST /api/match
- 后端返回后 progress 跳100%，停留300ms → 切换到结果页
- "已匹配"数字为模拟值（非真实进度）

## 五、待确认问题

1. **匹配性别筛选**：MVP 阶段不区分性别（男女都可能匹配到），是否需要在 Phase 1 就加入"只匹配异性"选项？这会显著影响用户体验
2. **1W 虚拟用户的性别比例**：当前设计为 50/50，是否需要调整为其他比例（如按实际用户群体性别比）？
3. **匹配结果是否排除自身**：如果用户输入的出生日期恰好与某个虚拟用户相同，是否需要排除该条结果？
4. **Top-N 默认值**：默认返回 Top 5 是否合适？还是默认 Top 3 更聚焦？用户可调整范围 1-20 是否合理？
5. **免责声明措辞与位置**：需要在页面哪里展示免责声明？是否需要用户勾选确认"了解仅供娱乐"后才能匹配？
6. **合盘评分权重可调**：权重外置到 config.py 后，是否需要提供管理界面让运营调整？还是只通过修改配置文件？
7. **分享功能形态**：Phase 3 分享是生成图片截图还是生成短链接？如果是短链接，需要后端存储匹配结果，增加系统复杂度
8. **移动端最低兼容**：是否需要兼容微信内置浏览器？是否需要考虑 iOS Safari 的特殊适配？
9. **排盘边界精度**：sxtwl 在立春精确时刻（如 02:00 立春，01:59 出生）的处理是否需要人工校验案例？
10. **数据更新策略**：1W 虚拟用户是否需要定期更新（如新增用户名/调整年龄分布）？还是一次性生成永久使用？
