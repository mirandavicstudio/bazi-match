## 一、选型依据

| 方案 | 是否选用 | 理由 |
|------|---------|------|
| SQLite 3 | ✅ 选用 | 1W 条数据，零配置，单文件部署，Python 内置支持 |
| MySQL | ❌ 不选用 | 杀鸡用牛刀，1W 数据完全不需要 |
| PostreSQL + pgvector | ❌ 不选用 | 本项目无向量搜索需求（合盘是规则打分，非向量检索） |
| JSON 文件 | ❌ 不选用 | 无法做结构化查询，全量读取性能差 |

**结论**：SQLite 完全够用，且部署最简单。

## 二、表结构设计

### 2.1 `users` 表（核心表）

存储 1W 名虚拟用户的基础信息和预计算的八字数据。

```sql
CREATE TABLE IF NOT EXISTS users (
    -------- 主键 --------
    id              INTEGER PRIMARY KEY AUTOINCREMENT,

    -------- 基础信息 --------
    name            TEXT    NOT NULL,                 -- 姓名（百家姓 + 常见名随机组合）
    gender          TEXT    NOT NULL,                 -- "男" 或 "女"
    birth_year      INTEGER NOT NULL,                -- 出生年份（如 1990）
    birth_month     INTEGER NOT NULL,                -- 出生月份（1-12）
    birth_day       INTEGER NOT NULL,                -- 出生日（1-31，按月份有效）
    birth_hour     INTEGER NOT NULL,                -- 出生小时（0-23）
    birth_minute    INTEGER NOT NULL DEFAULT 0,      -- 出生分钟（0/15/30/45）

    -------- 预计算八字（避免每次匹配重新算）--------
    year_pillar     TEXT    NOT NULL,                 -- 年柱（如 "庚辰"）
    month_pillar    TEXT    NOT NULL,                 -- 月柱（如 "己卯"）
    day_pillar      TEXT    NOT NULL,                 -- 日柱（如 "壬申"）
    hour_pillar     TEXT    NOT NULL,                 -- 时柱（如 "甲辰"）

    -------- 日主（用于日主关系计算）--------
    day_master      TEXT    NOT NULL,                 -- 日干（如 "壬"）

    -------- 五行分布（JSON 字符串存储）--------
    wuxing_dist    TEXT    NOT NULL,                 -- JSON：{"金":1,"木":1,"水":1,"火":2,"土":3}

    -------- 纳音（用于纳音维度计算）--------
    nayin           TEXT    NOT NULL,                -- 年柱纳音（如 "白蜡金"）
    nayin_wuxing   TEXT    NOT NULL,                 -- 纳音五行（如 "金"）

    -------- 天干地支展开（用于快速匹配，避免每次解析）--------
    tian_nos       TEXT    NOT NULL,                 -- 全部 4 个天干（JSON 数组，如 ["庚","己","壬","甲"]）
    di_zhis        TEXT    NOT NULL,                 -- 全部 4 个地支（JSON 数组，如 ["辰","卯","申","辰"]）

    -------- 索引辅助字段 --------
    created_at      TEXT    NOT NULL DEFAULT (datetime('now', 'localtime')),  -- 创建时间
    updated_at      TEXT    NOT NULL DEFAULT (datetime('now', 'localtime'))   -- 更新时间
);

CREATE INDEX IF NOT EXISTS idx_users_gender     ON users(gender);
CREATE INDEX IF NOT EXISTS idx_users_birth_year ON users(birth_year);
CREATE INDEX IF NOT EXISTS idx_users_day_master  ON users(day_master);
```

#### 字段设计说明

| 设计决策 | 理由 |
|---------|------|
| 八字四柱拆成 4 个字段 | 方便按柱查询（虽然本项目不需要，但预留扩展性） |
| `wuxing_dist` 存 JSON | SQLite 无原生 JSON 类型，用 TEXT 存储 JSON 字符串，Python 侧 `json.loads()` 解析 |
| `tian_nos` / `di_zhis` 存 JSON | 匹配时需要遍历天干地支，预存展开数组避免每次重新解析四柱 |
| 加 `gender` / `birth_year` 索引 | 后期可能加筛选条件（"只看女性"、"年龄相近"） |
| `created_at` / `updated_at` | 数据审计，调试用 |

### 2.2 `match_history` 表（可选，Phase 2 实现）

记录每次用户的匹配历史，用于"再看一次上次结果"功能。

```sql
CREATE TABLE IF NOT EXISTS match_history (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    user_input      TEXT    NOT NULL,        -- 用户输入的八字（JSON 字符串）
    matched_user_id INTEGER NOT NULL,        -- 匹配到的用户 ID（外键 → users.id）
    match_score     REAL    NOT NULL,        -- 匹配分数（0-100）
    match_grade     TEXT    NOT NULL,        -- 等级（"天作之合"等）

);

CREATE INDEX IF NOT EXISTS idx_match_history_created_at ON match_history(created_at DESC);
```

**Phase 1（MVP）不需要此表**，等到要做"历史记录"功能时再加。

## 三、数据生成规范（`seed.py`）

### 3.1 姓名生成

```
姓氏池：前 100 个中国常见姓（李、王、张、刘、陈、杨、赵、黄、周、吴...）
男名池：50 个常见男名（伟、强、磊、军、勇、杰、涛、明、辉、鹏...）
女名池：50 个常见女名（芳、娟、丽、秀英、敏、静、丽华、婷...）

生成规则：
  姓名 = 随机选姓 + 随机选名（不保证男女名和性别严格对应，但概率上 95% 对应）
```

### 3.2 出生日期生成

**目标**：生成分布接近中国真实人口年龄分布的虚拟用户。

```
出生年份分布（正态分布，均值 = 1995，标准差 = 10）：
  - 1980-1990：约 20%
  - 1990-2000：约 50%（主力适婚年龄）
  - 2000-2010：约 30%

出生月份：1-12 均匀分布
出生日：按月份有效日期随机
出生时辰：0-23 均匀随机（后期可偏重于"白天出生多"，但 MVP 不需要）
```

### 3.3 八字预计算

每条用户记录，在 `seed.py` 生成时**立即调用 `paipan.get_sizhu()` 计算八字**，将结果存入对应字段。

```python
# 伪代码
for i in range(10000):
    birth = generate_random_birth()
    bazi = paipan.get_sizhu(birth.year, birth.month, birth.day, birth.hour, birth.minute)

    insert_user(
        name=generate_name(birth.gender),
        gender=birth.gender,
        birth_year=birth.year,
        ...,
        year_pillar=bazi.year_pillar,
        month_pillar=bazi.month_pillar,
        ...
        wuxing_dist=json.dumps(bazi.wuxing_dist),
        tian_nos=json.dumps([bazi.year_pillar[0], bazi.month_pillar[0], ...]),
        ...
    )
```

**为什么预计算？**

| 方案 | 做法 | 匹配时耗时 |
|------|------|-----------|
| 预计算（选用） | `seed.py` 生成时算好，存数据库 | 匹配时直接读，无需再算 |
| 实时计算（不选用） | 匹配时临时调用 `get_sizhu()` | 1W 条 × 5ms = 50s，完全不可接受 |

## 四、数据库操作层设计（`db.py`）

### 4.1 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 驱动 | Python 内置 `sqlite3` | 无需额外安装，SQLite 官方驱动 |
| 连接管理 | 单例连接（模块级 `conn` 对象） | 1W 数据量极小，无需连接池 |
| 数据转换 | `sqlite3.Row` + 手动转 `dict` | 简单直接，无额外依赖 |

### 4.2 核心函数

```python
# 初始化
init_db() -> None
  - 执行 CREATE TABLE（IF NOT EXISTS）
  - 创建索引（IF NOT EXISTS）

# 写入
insert_user(user: dict) -> int          # 插入单条，返回新 ID
batch_insert_users(users: list[dict]) -> int  # 批量插入，返回成功条数
clear_users() -> None                  # 清空表（用于重新播种）

# 读取
get_all_users() -> list[dict]         # 全量读取（匹配时遍历用）
get_user_by_id(uid: int) -> dict | None
get_users_by_gender(gender: str) -> list[dict]  # 可选，按性别筛选
count_users() -> int                  # 统计总条数

# 删除（可选）
delete_user_by_id(uid: int) -> bool
```

### 4.3 `get_all_users()` 性能考虑

**问题**：1W 条全量读取，SQLite 内存占用多少？

```
每条记录约 500 字节（含所有字段）
1W 条 = 约 5 MB
完全在内存可接受范围内。
```

但 `get_all_users()` 返回 list[dict]，这 5MB 数据会常驻内存（匹配期间）。可接受。

**优化方案（Phase 3）**：

如果后期数据量增大（> 5W 条），可以改为：
- 先读 ID + 预计算字段（八字、五行），不考虑姓名等展示字段
- 匹配完成后再按 ID 查详情

但 **Phase 1 完全不需要**，1W 条全量内存无压力。

## 六、数据一致性保障

### 6.1 `seed.py` 幂等性

**问题**：如果多次运行 `seed.py`，会不会产生重复数据？

**解决方案**：`seed.py` 开头先检查 `count_users() == 0`，若已有数据则询问用户"是否清空后重新生成"。

```python
# seed.py 伪代码
if count_users() > 0:
    print(f"数据库中已有 {count_users()} 条用户，是否清空后重新生成？(y/N)")
    if input().lower() != 'y':
        sys.exit(0)
    clear_users()
```

### 6.2 事务管理

`batch_insert_users()` 使用 SQLite 事务：

```python
def batch_insert_users(users):
    conn = get_conn()
    cursor = conn.cursor()
    try:
        conn.execute("BEGIN")
        for u in users:
            cursor.execute("INSERT INTO users (...) VALUES (...)")
        conn.commit()
        return len(users)
    except Exception as e:
        conn.rollback()
        raise e
```

**好处**：若中途失败（如磁盘满），不会留下部分数据。

## 九、扩展讨论（Phase 3 考虑）

### 9.1 数据量增大后怎么办？

| 数据量 | 方案 |
|--------|------|
| 1W 条 | 当前设计完全够用 |
| 10W 条 | `get_all_users()` 返回 50MB 数据，内存有压力 → 改按性别/年份筛选后读取 |
| 100W 条 | 需要加索引 + 粗筛（按五行分布预筛）→ SQLite 可能不够，考虑 MySQL |

### 9.2 是否需要分表？

**不需要**。1W 条数据，单表完全够用。即使到 100W 条，SQLite 也能扛（前提是加好索引）。

### 9.3 是否需要数据库迁移工具（如 Alembic）？

**MVP 不需要**。`users` 表结构固定，不会有复杂迁移需求。若后期要改表结构，直接手写 `ALTER TABLE` 或删库重建即可。
